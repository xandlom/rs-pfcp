# Cross-library verification: rs-pfcp ↔ go-pfcp

rs-pfcp's own test suite is self-referential: `marshal`/`unmarshal` round trips
are checked against each other. If both are wrong in the same consistent way
— which is exactly what happened with `UsageReportTrigger::new` placing
compatibility bits in the wrong octet — a round trip is the identity function
and passes anyway. This directory cross-checks rs-pfcp against an independent
implementation ([go-pfcp](https://github.com/wmnsk/go-pfcp) v0.0.24) to catch
that class of bug, plus other classes a single-implementation test can't see
(framing/length errors, dropped IEs, decode/re-encode asymmetry).

See `docs/analysis/pr-62-flygoat-review.md` for the bug that motivated this.
The full design rationale is summarized below.

## Two legs, two different bug classes

### 1. Fixture semantic check (`tests/fixture_semantic_check.rs`)

For a handful of named bitmap-IE intents (e.g. "Apply Action = FORW"),
`interop/go/cmd/gen-fixtures` used go-pfcp to emit canonical bytes **once**,
inlined as `&[u8]` literals directly in `tests/fixture_semantic_check.rs`.
`cargo test --test fixture_semantic_check` asserts rs-pfcp's own construction
for the same named intent matches those bytes exactly. No network, no Go
toolchain needed to *run* it — only to regenerate the byte literals if the
intent list changes (they're small enough — 5-6 bytes each — that a committed
fixtures directory would be more machinery than the bytes are worth).

This is the leg that catches a *symmetric* bug: if rs-pfcp's `unmarshal` and
`marshal` for some flag are both wrong in the same way, decoding rs-pfcp's own
output can never reveal it. Diffing against an independently-generated byte
sequence does.

**Regenerating the byte literals** (only needed if the intent list in
`interop/go/cmd/gen-fixtures/main.go` changes): run the generator, which
prints ready-to-paste Rust array literals, and copy the ones that changed
into the matching `check(...)` call in `tests/fixture_semantic_check.rs`.
```bash
cd interop/go/cmd/gen-fixtures && go run main.go
```

### 2. Echo/verify exchange (Components 2+3 of the plan)

- `examples/interop-echo-msg` (rs-pfcp) and `interop/go/cmd/echo-msg-server`
  (go-pfcp) are generic message echo servers: decode whatever PFCP message
  arrives, re-encode it, send it back. Both bind `127.0.0.1:8805` by default
  (override with `INTEROP_ECHO_ADDR`).
- `interop/go/verify/verify_test.go` (`go test`) and `tests/interop_verify.rs`
  (`cargo test --test interop_verify -- --ignored`, deliberately excluded
  from the default `cargo test` run since it needs a live peer) each build a
  minimal-valid instance of every overlapping message type, send it to the
  *other* library's echo server, and check the echoed reply against the
  original — structurally (message type, SEID, key IE fields via
  `rs_pfcp::comparison::MessageComparator` on the Rust side / go-pfcp's typed
  accessors on the Go side), not as a raw byte diff.
- `interop/run-cross-verify.sh` is the single entrypoint: builds both echo
  servers, runs both directions sequentially against the same port 8805 (see
  "Why sequential, why one port" below), captures each direction's traffic
  with `tcpdump`, and checks the capture with `tshark`'s built-in PFCP
  dissector — a third, independent check that neither library's own
  understanding of the spec is systematically wrong in a way a two-party diff
  wouldn't reveal.

**Running locally:**
```bash
./interop/run-cross-verify.sh
```
Needs: Go 1.21+, `tcpdump` with `cap_net_raw` (unprivileged capture — see
below), `tshark`. Without `tcpdump`/`tshark` present the script still runs
both verify suites and skips the pcap checks for that direction with a
warning.

### Why sequential, why one port (8805)

Wireshark's PFCP dissector auto-registers on UDP 8805 with no extra `-d`
flags needed. Running both directions on distinct ports to allow
concurrency would mean passing `-d udp.port==NNNN,pfcp` per port and getting
it wrong once; running them sequentially on the one port PFCP actually uses
keeps the tshark invocation trivial. The bare-IE echo mode (deferred, see
below) isn't valid standalone PFCP and was never going to get a tshark check
regardless of port.

### Unprivileged tcpdump capture

```bash
sudo setcap cap_net_raw,cap_net_admin=eip "$(command -v tcpdump)"
```
CI does this automatically (see `.github/workflows/interop.yml`); locally
you only need it once per machine.

## What a green run proves — and doesn't

- **Fixture check green**: rs-pfcp's encoding for the specific bitmap-IE
  intents in the fixture list matches go-pfcp's, byte for byte.
- **Echo/verify green**: header/length/SEID/message-type-dispatch parity
  across the 23 overlapping message types, decode→re-encode fidelity in both
  directions, and — from the tshark leg — no dissector-level malformed/error
  frames in the actual wire traffic.
- **Neither proves**: general IE-semantic correctness beyond what's covered.
  Minimal-valid message instances are mostly header + 1-2 mandatory IEs (a
  few, like Session Deletion Request, are effectively header-only) — this
  does not exercise the other ~340 IE types, grouped-IE depth, multi-instance
  repeated IEs, or edge-case field values. It's a floor, not a ceiling.

## Known gaps

- **go-pfcp v0.0.24 doesn't implement `SessionSetModificationRequest`/
  `Response`** (rs-pfcp has 25 message types, go-pfcp has 23 overlapping ones
  — these two are exactly the pair PR #62 added). Both verify suites skip
  them explicitly with a comment; there's no cross-check for this message
  type until go-pfcp adds support or a second reference implementation is
  used.
- **Resolved**: rs-pfcp's `UsageReportTrigger` used to be a single-octet,
  8-flag encoding (`PERIO`..`LIUSA` sharing one byte), disagreeing with
  go-pfcp v0.0.24's full extensible Release-18 layout (`LIUSA` at bit 2 of
  octet 2 there vs. bit 7 of the single octet on rs-pfcp `main`). PR #62
  (`cecbb2e`, merged) modernized rs-pfcp to the fixed 3-octet extensible
  form, so bit positions now agree between the two libraries. `LIUSA` is
  still not in the fixture set for `usage_report_trigger_*` (only
  `PERIO`/`VOLTH` are covered) — that's just the general "fixture-leg intent
  list is intentionally small" scoping under "Deferred to v2" below, not a
  remaining disagreement.

## Deferred to v2 (explicitly out of scope for this pass)

- Bare-IE echo mode (a second port, 8806) and its verify suites — for
  standalone IE round trips without a full message wrapper.
- Expanding the fixture-leg intent list beyond the six bitmap IEs already
  known to be risky.
- Expanding the message corpus beyond one minimal-valid instance per type
  (edge-case field values, multiple-instance repeated IEs, grouped-IE depth).
- Negative/malformed-input testing. The echo servers currently log and don't
  reply on a decode failure (v1's corpus is all valid-by-construction, so
  this path isn't expected to fire) — testing "this malformed input should be
  rejected" needs an explicit error-frame convention first.
- `SessionSetModificationRequest`/`Response` cross-check (blocked on go-pfcp
  support, or a second reference implementation).
- Extracting `interop/go/` into its own repository, the way
  [go-pfcp-interop](https://github.com/xandlom/go-pfcp-interop) (the
  existing full-session-lifecycle socket interop tests, a coarser-grained
  complement to this directory) already did.

## Layout

```
interop/
├── go/
│   ├── go.mod
│   ├── cmd/
│   │   ├── gen-fixtures/       # prints Rust byte literals, not run in CI
│   │   └── echo-msg-server/    # go-pfcp message echo daemon
│   └── verify/
│       └── verify_test.go      # go test, table-driven, one subtest per message type
└── run-cross-verify.sh         # orchestration: build, run both directions, tshark checks

examples/interop-echo-msg/      # rs-pfcp message echo daemon
tests/interop_verify.rs         # cargo test --test interop_verify -- --ignored
tests/fixture_semantic_check.rs # plain cargo test, no network; fixture bytes inlined as &[u8] literals
```
